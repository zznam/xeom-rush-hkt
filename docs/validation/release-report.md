## Production corner recovery

A real public keyboard journey exposed a GPS edge case after the twelve planned PRs merged: a rider beside a building corner was valid under circular physics but rejected by square navigation clearance. [Follow-up PR #19](https://github.com/zznam/xeom-rush-hkt/pull/19) shares the exact circular collision kernel and reconnects legal endpoints to the existing conservative street graph. Building interiors, monuments and active closures still reject routes. A core regression physically drives every recovery segment without collision correction; a browser regression reproduces the corner with real steering and completes the paid trip.

The ordinary [follow-up CI job](https://github.com/zznam/xeom-rush-hkt/actions/runs/37145150041/job/111267440686) passes 41 shared, 28 portable simulation and 60 server tests, four native KV tests and 38 browser journeys (24 public, three regional, ten private/team, one rollback), with no browser retries. Runtime adapters, builds, lint/format, Docker and Terraform checks also pass. The [ordinary local keyboard journey](natural-keyboard-journey.json) completes protected practice, a naturally generated paid passenger trip, shift results and the same guest's career reload without test position or reward endpoints. It uses the local Memory adapter in one server process; persistent Deno KV durability has its separate native test. Its headless macOS renderer measures 119fps median / 59.5fps p05 over 1,807 frames; this is a short ordinary workload, not the dense hosted soak or physical phone hardware.

A separate live profile check found that an already-normalized HTTPS backend URL was converted to HTTP, so the browser blocked career rankings as mixed content. The profile now uses the existing API URL helper. `secure-career.test.ts` forwards secure WebSocket frames to the actual local authoritative server and verifies the HTTPS ranking request and rendered row. It fails against the previous HTTP downgrade and passes with the fix. This profile-only change leaves the simulation, protocol, server, room owners and renderer measured by the corner-recovery soak unchanged.

The [merge ledger](release-merge-ledger.json) records all twelve planned PR heads, their successful rebased CI, merge commits and timestamps. All thirteen managed worktrees remain attached for review. The integration checkout is reused for the observed GPS follow-up.

Raw evidence: [baseline simulation](baseline-performance.json), [enhanced simulation](release-performance.json), [baseline browser sample](baseline-browser.json). Full snapshots in this deterministic comparison differ from the live adapter's full/delta and control traffic. Memory figures are end-of-sample observations, not reserved capacity or leak proof.

The latest [full-capacity report](release-soak.json), measured at GPS-recovery commit `a0424704d2a310d1f42692b0e70fd3d3b2fa1712` in [successful CI run 37145150041](https://github.com/zznam/xeom-rush-hkt/actions/runs/37145150041), passes the unchanged gates: 1,800,346ms elapsed, sixty uninterrupted samples, 5,634 deliveries, 49 rounds, zero errors and worst owner cumulative p95 of 36.3ms. All owners sustain at least 18Hz. Final public p95 is 36.3ms Node / 16.5ms Deno; ECS private owners measure 4.5–5.1ms. The same configured load observes all four day phases, rain, seven closures, all six demand events and all three job kinds. The subsequently staged profile HTTPS fix affects only the closed career dialog; measured simulation, protocol, adapters and renderer source are identical.

The latest dense hosted render measures desktop 12.75fps median / 9.18fps p05 and phone viewport 30.68fps / 21.74fps. Rendering remains modest at this synthetic density. Observed desktop heap is 15.2→26.0MB; phone 14.3→44.7MB. End Node RSS is 292.1MiB and Deno 189.3MiB. Raw peer traffic averages 34,352 bytes/second. These measurements do not prove leak freedom or a causal improvement over different hardware.

The [arrival-feedback capacity report](release-soak-arrival-feedback.json), from the successful [feedback-update soak job](https://github.com/zznam/xeom-rush-hkt/actions/runs/37139549164/job/111250954265), passes all acceptance assertions: 1,800,271ms elapsed, sixty uninterrupted samples, 5,619 deliveries, 49 rounds, zero errors and maximum cumulative p95 of 33.8ms across every measured owner. The [initial pre-merge soak](release-soak-premerge.json) also passed at 34.1ms worst owner p95, with 5,403 deliveries and 49 rounds. The later run's ordinary browser job exposed the idle-after-delivery assumption described above; its soak job passed, and the corrected browser assertion passes locally before fresh rebased CI. The previous [full run](https://github.com/zznam/xeom-rush-hkt/actions/runs/37132137585) completed 5,419 deliveries and 49 rounds with no errors, but was rejected because Node public p95 reached 40.8ms. Snapshot encoding now reuses at most 2,048 UTF-8 records and compares explicit binary fields. Its load is 74 public humans and 16 public bots, plus seven private/team rooms with 52 humans and four filler bots. All four configured ECS room slots and three Durable Objects run together. Two real renderers use desktop 1440×900 and phone 390×844. The feedback-update hosted run's desktop renderer measured 11.81fps median / 8.92fps p05; phone measured 30.02fps median / 21.37fps p05. This dense synthetic run has modest desktop rendering throughput despite meeting the server gate. Desktop observed heap rises from 15.2MB to 42.1MB; phone from 14.3MB to 26.0MB. End-of-run Node RSS is 289.5MiB and Deno RSS 188.1MiB. Live raw-peer traffic averages 34,795 bytes/second, including private-room metadata. These observations are retained rather than treated as proof of a rendering speedup or a memory-leak check.

The baseline browser run lasts sixty seconds on the shared macOS host; the full release run uses an isolated hosted Linux runner. FPS, heap and live bandwidth remain useful recorded observations, but their hardware, duration, driver activity and room populations differ. They do not establish a causal rendering speedup or like-for-like bandwidth reduction.
